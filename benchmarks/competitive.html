Competitive position & standardized performance

Head-to-head against libsodium (via PyNaCl 1.6.2) and OpenSSL (via cryptography 49.0.0), same host, same process, same parameter sets. Peer libraries are benchmark-only comparison targets and are not linked into the production library; INVARIANT-36 forbids a peer implementation as a correctness answer key, which this is not — it is a speed reference only. Wins and losses are both shown.

1 · Where AMA stands against libsodium and OpenSSL

Ratio of AMA throughput to the peer's, log-scaled around parity. Right of the centre line AMA is faster; left, the peer is. Every bar is labelled, so nothing is read from colour or length alone.

Ed25519 and AES-GCM measured through each library's Python binding (benchmarks/comparative_benchmark.py); ML-DSA/ML-KEM measured directly against cryptography.hazmat.primitives.asymmetric.mldsa/mlkem at matching parameter sets. ML-DSA signing is rejection-sampled, so its cost depends on the message: these figures use 256 distinct random messages. A single fixed message measured 4.57× — that number would have been an artefact, and is not used.

The AES-GCM gap is a deliberate security choice, not a deficiency. This CPU exposes AES-NI, and OpenSSL uses it. AMA ships a constant-time bitsliced AES as the default (INVARIANT-20: “Constant-Time AES Must Remain the Default”), which never indexes a lookup table with key-dependent data and so is immune to the cache-timing attack class that broke table-driven AES. Table-based AES exists behind AMA_AES_TABLE_INSECURE and is opt-in, off, and named to be hard to enable by accident. The throughput cost of that choice is the bar you see; it is the price of the property, and it is stated rather than hidden.

2 · Standardized performance — cycles per byte

Cycles/byte is the metric eBACS and Crypto++ report, because it is the one that survives a change of clock speed: it isolates implementation efficiency from how fast the machine happens to run. Lower is better. Measured on the raw C harness (build/bin/benchmark_c_raw), so no FFI overhead is counted, at a measured 2.80264 GHz.

cycles/byte = clock ÷ (bytes ÷ second). Bulk figures are taken at 16–64 KiB where the per-call setup cost has amortised; the short-message rows are shown separately below because at 32 bytes a sponge's fixed permutation dominates and the ratio says more about call overhead than about the primitive.

Throughput and scalability by message size

The same primitives as bulk throughput in MB/s, swept across message size. The curve shape is the point: AEAD throughput climbs with message size until the per-call setup is amortised, then flattens — the plateau is the primitive's real speed, and the left-hand rise is the cost of calling it.
