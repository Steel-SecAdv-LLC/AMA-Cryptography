    secp256k1 — fixed-base comb vs. Montgomery ladder

    Public-key derivation and the ECDSA signing nonce both compute d·G against the compile-time generator. Both used the generic Montgomery ladder, which spends one addition and one doubling per scalar bit because it must not branch. A 4-block precomputed comb replaces 256 of each with 64. Verification is deliberately unchanged — it is variable-time by design and already uses Shamir's trick. Raw C, µs/op.

    Constant-time preserved (INVARIANT-12): Welch's t-test over 60,000 samples gives fixed-vs-random |t| = 0.29 and a Hamming-weight split of |t| = 1.03, against dudect's leakage threshold of 4.5.

    Measured ÷ floor, against the old floors

    What the regression gate was actually comparing before this recalibration. The floors were calibrated against v2.1.2 and declared valid through v3.0.0 while the library shipped 3.4.0 — and nothing read that field, so the gate kept reporting PASS against four-release-old numbers. A ratio of 18× means throughput would have to fall 94 % before the gate noticed; a gate that cannot fail is worse than no gate, because it manufactures assurance. Bars below 1.0 are the opposite problem — a floor already at or above what this host delivers — and are marked in red.

    New floors are 0.65 × min(measured, canonical) per the project's documented 35 %-headroom convention, so a floor can never exceed what the canonical runner achieves. No floor was lowered: where this host measures slower than canonical (AES-GCM, X25519) the existing floor stands. That combination is what makes the recalibration robust to this host's run-to-run variance — the canonical cap absorbs high outliers and the never-lower rule absorbs low ones. AES-GCM is the one entry to watch: its floor was already above this host's throughput before any change here, so it clears the gate only on the 40 % tolerance. It needs a canonical-runner measurement, not a floor edit.
